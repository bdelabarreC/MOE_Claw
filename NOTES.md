# MOE-CLAW — session notes / open issues

## OPEN: incremental indexing re-reads every file

`moeclaw_update.py` currently classifies **every** file as new/changed on each
run, so it reindexes the whole folder instead of just the stale ones. The merge
logic itself is verified (see "What is known good" below) — the bug is in the
staleness comparison.

### Leading suspect: timezone mismatch between SVL and Python

The comparison works by matching the `file_date` recorded in the CSV (written by
`moe_claw.svl` via `clock_to_timeYMD`) against the file's current mtime read by
Python (`datetime.fromtimestamp`, which uses **local** time).

If MOE's `clock_to_timeYMD` returns **UTC** while Python returns **local**, every
file looks shifted by the UTC offset (4–5 h in US Eastern) and therefore
"changed" on every run. That matches the symptom exactly.

**Diagnostic — run these two and compare:**

1. In MOE, for a known file:
   ```
   svl> iso_date fdate 'G:/path/to/some.moe'
   ```
2. In Python, same file:
   ```python
   import datetime, os
   p = r"G:\path\to\some.moe"
   print("local:", datetime.datetime.fromtimestamp(os.path.getmtime(p)))
   print("utc  :", datetime.datetime.utcfromtimestamp(os.path.getmtime(p)))
   ```

- If SVL matches **local** → timezone is not the cause; look at cause #2/#3.
- If SVL matches **utc** → fix by making both sides agree. Cleanest is to have
  Python compare in UTC (`utcfromtimestamp`) so the CSV stays as MOE writes it.

### Other candidates (check if timezone is ruled out)

2. **Stale CSV without dates.** If `moe_index.csv` was generated by an older SVL
   that had no `file_date` column, `recorded` is empty and *everything* counts as
   new. Confirm the CSV's header is:
   `file,file_date,compound,n_res,n_atoms,mw,smiles`
   and that the date column is actually populated.

3. **Google Drive mtimes.** Files under `G:\My Drive\...` are on Drive File
   Stream; mtimes can shift on sync/rehydrate, which would legitimately make
   files look changed. Test on a **local** folder (e.g. `C:\temp\moe_test`) to
   isolate this from the timezone question.

4. **Basename vs path.** The CSV stores `ftail` (basename); `scan_dir()` keys on
   basename too, so this should match — but worth confirming no path leaked in.

### Quick way to see what it thinks

```
python moeclaw_update.py --dir DIR --dry-run
```
Never starts MOE; just prints which files it considers new vs changed vs
unchanged. Add a temporary print of `recorded[name]` vs
`iso_from_mtime(mtime)` for one file to see the two strings side by side —
that will identify the mismatch immediately.

## What is known good (verified this session)

- **`ArgvPull ['-file', 1]` returns ALL values wrapped in an outer vector**
  (e.g. `[[a,b,c]]`). Use `cat` to flatten, then `length` for a reliable scalar.
  Do **not** test the raw result with `isnull` or `=== ''` — neither works, and
  that combination causes an infinite loop.
- **`asctime` is unusable here** — it ignores its clock argument and returns the
  *current* time. Use `clock_to_timeYMD`. (Verified: raw epoch matched
  `clock_to_timeYMD`, not `asctime`.)
- **`aSetForceRS [atoms, aRSChirality atoms]`** before `sm_ExtractUnique` is what
  makes SMILES isomeric; without it MOE exports flat structures.
- **Merge logic in `moeclaw_update.py` is correct**, tested against a mocked
  moebatch across 9 scenarios: skip-when-unchanged, new file, changed file,
  deleted file purge, `--force`, `--dry-run`, and — importantly — a file
  re-indexed with *fewer* compounds correctly drops its stale rows instead of
  accumulating duplicates. A moebatch failure leaves the master CSV untouched.
- **v8 browser** handles missing `file_date` gracefully (hides date controls).
